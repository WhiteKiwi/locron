# Dashboard cookie and CSRF token admission

Refs #30. Stacked on the separate security-header Draft #142, exact parent `507777cedd5bd02b162d9b347c2770cdf4585bc0`; this plan precedes implementation. The existing dashboard security contract already issues 64-character hexadecimal session/CSRF values, supports cookie-authenticated browser mutations and exempts valid bearer authentication. No new authentication scheme, route or token issuance policy is introduced.

## Source-established gaps

The middleware selects the first Cookie field and the first matching cookie, compares arbitrary CSRF strings (including two empty strings), and selects the first CSRF header or form value. An unreadable CSRF header becomes an absent header and can fall back to a form. The form content-type check accepts any prefix, and buffering takes the entire Request, losing its metadata on a failed body read. These are source observations, not a demonstrated browser exploit or production incident.

## Approach and Verify

1. Read the named session/CSRF cookie across all Cookie fields and require exactly one plain 64-hex value. Reject duplicate target names even when values agree, empty/malformed target values and undecodable fields; unrelated cookies and split fields stay supported. Verify combined and split Cookie fields, correct values, duplicate same/different values, malformed target syntax and invalid lengths/characters, while preserving bearer and public-entry behavior. RFC 9113 section 8.2.3 permits splitting Cookie fields and prescribes semicolon joining; do not reject every repeated Cookie field as inherently invalid: https://www.rfc-editor.org/rfc/rfc9113.html#section-8.2.3 .
2. Require one decodable, well-formed CSRF header when supplied, reusing #142's single_header helper. Only genuine absence may inspect the form. Verify a present invalid/empty/duplicate header cannot be rescued by an otherwise valid form; valid 64-hex values still compare exactly with the cookie through the existing constant-time comparison. Preserve safe-method, bearer and unauthenticated-paste exemptions, statuses/codes and generic no-value-reflection errors.
3. Restrict form detection to one content-type with the exact urlencoded media-type essence, retaining parameters and case-insensitive media-type comparison. Buffer only the body with the existing 1 MiB cap, retain request metadata, require valid UTF-8 and one plain 64-hex csrf_token field, and restore successfully buffered bytes for the handler. Verify duplicate/bare/empty/malformed fields, unrelated fields, invalid media-type suffixes, Unicode errors, read/cap failures and exact request body/header/extension preservation on successful buffering. The plain-hex field contract remains unchanged; this is not a general percent-decoding form parser.

The code Draft changes only middleware parsing and CSRF admission. It does not change token creation/rotation, session-status cookie repair, CSRF issuance, route handlers, dependencies, workflows, body limits or shutdown clocks. A malformed browser cookie may require the existing token-paste flow to obtain a fresh cookie. Complete browser/native regression coverage, formatting, server library/contract tests, warnings-denied Clippy and independent review remain required before merge.
